# Sport Buddy — промпти для вайб-кодінгу (лаба №5)

## Як цим користуватись (10 хвилин підготовки)

1. Створи порожню папку проєкту, поклади в неї **папку `docs/` з цього пакета** (SPEC, DESIGN, mockups). Claude Code не відкриє твої Figma/Confluence-посилання, тому все потрібне для нього має лежати у файлах.
2. Відкрий термінал у цій папці, запусти `claude`.
3. Встав **Промпт 0** (нижче). Він просить спочатку план, а не код — це перша ітерація з методички.
4. Далі йди по промптах 1→5 по одному. Після кожного: запусти застосунок, пройди сценарій руками, тільки тоді наступний промпт.
5. Кожен промпт і кожну помилку з консолі зберігай у нотатки — це 3–5 «ключових промптів» і розділ «Промпти для виправлення помилок» у звіті.

Що треба зробити руками (Claude Code за тебе цього не зробить, він підкаже кроки): створити безкоштовний проєкт у Supabase і вставити ключі в `.env.local`; створити GitHub-репозиторій; підключити Vercel; додати викладача колаборатором.

## Роль

## Завдання
Створити вебзастосунок «Sport Buddy» — маркетплейс для пошуку компанії на спільні тренування (біг, теніс, футбол, велоспорт). Це MVP для навчальної лабораторної роботи, його має бути легко запустити й показати викладачу.

Ключова цінність — картка тренування, де кількість вільних місць і аватарки підтверджених учасників оновлюються в реальному часі без перезавантаження; плюс чат учасників і карта місця збору.

Повна специфікація (історії користувача, критерії приймання, тексти помилок, граничні випадки) — у `docs/SPEC.md`. Дизайн-система (кольори світлої/темної теми, типографіка, компоненти) — у `docs/DESIGN.md`. Бачення продукту (Vision Board) — зображення `docs/vision-board.png`. Екрани — у `docs/mockups/` (wf-* — вайрфрейми, mock-*-light/dark — фінальний вигляд). Прочитай ВСІ ці файли й подивись усі зображення перед тим, як щось пропонувати. Важливо: джерело істини щодо поведінки, правил і текстів — бачення продукту й `docs/SPEC.md`. Мокапи — це ПРИКЛАД стилю й розкладки, а не вимога копіювати їх буквально (на них є розбіжності зі SPEC: напр. скасування «за 2 години», місто Харків — правильно 12 годин і Київ). Якщо щось суперечить одне одному, діє SPEC; про кожну суперечність скажи мені.

Сценарій, який має працювати від початку до кінця: «Я реєструюсь → шукаю тренування, фільтрую за спортом і рівнем → відкриваю картку → натискаю "Записатися" → бачу, що вільних місць стало менше, а моя аватарка з'явилась → відкриваю чат тренування. З іншого акаунта я як Організатор створюю тренування, у вкладці "Заявки" підтверджую чи відхиляю кандидатів».

## Технологічний стек
- Vite + React 18 + TypeScript (strict), React Router.
- Tailwind CSS; кольори й шрифти з DESIGN.md винести в CSS-змінні та Tailwind theme; темна тема через клас `dark`, початкове значення з `prefers-color-scheme`, перемикач у профілі/шапці.
- Supabase: Auth (email + пароль), Postgres, Row Level Security, Realtime. Бізнес-логіка, яка має бути атомарною (запис на тренування, підтвердження заявки, скасування), — у SQL-функціях (RPC) з блокуванням рядка, а НЕ в клієнтському коді.
- Карта: Leaflet + OpenStreetMap (без ключів API). Геокодування адрес: Nominatim з debounce і обмеженням частоти.
- Тести: Vitest для чистої логіки (валідація форми, обчислення вільних місць, фільтри); Playwright — лише 1–2 наскрізні сценарії наприкінці.
- Деплой: Vercel. Секрети тільки в `.env.local` (у `.gitignore`) і в змінних Vercel; `.env.example` у репозиторії.
Не додавай інших великих залежностей без пояснення, навіщо.

## Вимоги до інтерфейсу
- Mobile-first, коректно від 360 px; на десктопі контент центрується в колонці ~480 px (як застосунок), нижня навігація «Пошук · Створити · Заявки».
- Візуально — у стилі `docs/mockups/mock-*` в обох темах (це орієнтир, не піксель-перфект): Montserrat, помаранчева основна кнопка, бірюзові чипи й «Вільно N з M», аватари-ініціали. Дані й тексти — зі SPEC.
- Усі тексти українською, дослівно як у SPEC (він переважає над текстами на мокапах) (повідомлення про помилки, «Місць немає», «Ви записані», «Дані можуть бути неактуальними»).
- Стани: loading (skeleton), empty, error для кожного списку й форми; доступність з клавіатури, aria-label на іконках.
